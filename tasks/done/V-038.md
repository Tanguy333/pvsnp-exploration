# V-038 — Moteur turbo : énumération ET LLL compilés en code machine (Numba/LLVM)

**Date** : 2026-06-12
**Statut** : ✅ validé et déployé (15e auto-correction en cours de route, voir §3)
**Script** : `checks/svp_turbo.py` (+ marcheur générique `checks/march_turbo.py`)

## 1. Origine — la question de Tanguy

« Faisons-nous bien la recherche en C pour avoir plus de rapidité que Python ? »
Réponse honnête : non. `svp_fast` (V-036) avait remplacé les Fractions exactes
par des flottants (×8-25) mais restait du bytecode interprété (~150 ns/nœud).
Numba (JIT LLVM, installable par pip, sans chaîne MSVC) compile la boucle
numérique en code machine : ~2-5 ns/nœud — la vitesse d'un programme C.

## 2. Architecture (mêmes garanties d'exactitude que V-036)

- `_enum` (njit) : zigzag de Schnorr-Euchner, rayon rétrécissant flottant,
  tous les candidats sous rayon collectés (tampon avec compactage in situ),
  puis **vérification exacte en entiers Python** de chaque candidat —
  minimum et minimaux retournés exacts.
- `_lll` (njit) : LLL incrémental (Cohen 2.6.3) **avec GSO rafraîchi depuis
  les lignes exactes toutes les 4m permutations et certification finale sur
  GSO frais** (hystérésis δ−0,002 contre l'oscillation) ; en cas d'échec de
  certification ou d'entrée ≥ 2⁴⁰, repli automatique sur le LLL Python exact.
  Toutes les opérations de lignes sont entières → le réseau est exactement
  préservé quoi qu'il arrive aux flottants.

## 3. L'incident (15e auto-correction) — le LLL purement incrémental dérive

Première version de `_lll` : mises à jour incrémentales pures, sans
rafraîchissement. Symptôme attrapé par la batterie de validation : à (7, 40),
minima égaux mais **ensembles de minimaux divergents**, puis explosion du
temps d'énumération (run tué par Tanguy). Diagnostic : déterminants de Gram
identiques (réseau préservé ✓) mais plus petite norme GS de la base sortie
**7,4×10⁻⁷ contre 9,5** pour l'ancienne — huit ordres de grandeur de dérive
des μ accumulée, base quasi dégénérée, arbre d'énumération explosif. C'est
précisément pourquoi l'ancien `lll_reduce` recalculait tout le GSO à chaque
pas (stable mais O(m⁵)). Le correctif (fenêtres + certification) garde la
stabilité de l'ancien et la vitesse du compilé.
